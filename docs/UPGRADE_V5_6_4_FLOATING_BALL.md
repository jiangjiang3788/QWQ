# QWQ V5.6.4 悬浮球信息重构说明

## 核查结论

### 1. 原“来源完整”不等于语义来源完整

旧版 `coverage.complete` 只表示最终请求文本已被来源清单或兜底规则覆盖，不表示收藏、记忆等每一种业务来源都被单独识别。收藏来源虽然已在来源注册表登记为 `collection.relevant`，但私聊来源构建器没有提取 `【用户收藏的内容】` 区块，因此收藏正文被并入 `system.core_rules`，界面不会出现独立收藏项。

V5.6.4 将收藏区块从最终 system prompt 中按原文提取，并以“相关收藏”独立显示；每条 `- 内容：...` 直接显示实际发送正文。

### 2. 结构化记忆过去有来源，但没有表格/记录视图

旧版会记录 `memory.structured`，但只保存为一个大文本块。V5.6.4 按 `【表名】` 和 `---` 分隔符拆为表格及记录条目，界面显示本次请求中实际发送的记录正文。

### 3. “202 条消息”是真实请求数组长度，但不是 202 轮对话

`ai_request_runtime.js` 在网络发送前读取最终请求体，并记录消息数组长度：OpenAI 兼容接口对应 `messages.length`，Gemini 对应 `contents.length`。Gemini 的 `system_instruction` 独立计数，不属于 `contents`。

聊天历史窗口由 `db.magicRoom.contextPolicy.historyCount` 控制。设置入口是 Proment / 魔法屋的“聊天条数”，界面允许 1—200，编译器内部容许 1—500，默认 30。单位是单条消息，用户消息和角色消息分别计数，不是成对的对话轮次。

悬浮球“操作记录”是另一套数据：只记录最近 20 次操作，保存在当前浏览会话的 `sessionStorage`，与聊天历史数量没有关系。

### 4. 记忆写入过去只显示内部标识

旧版聊天消息变化会保存实际正文，但结构化记忆 sidecar 只记录 `tableId / recordId` 摘要。V5.6.4 在写入完成后读取实际表和记录，保存表名、字段名、格式化后的记录正文。界面不再把内部 ID 作为主要信息，并明确显示：

- 已写入记忆及实际内容；
- 已检查但本轮无记忆变化；
- 记忆写入失败及原因。

## 新的信息层级

1. 顶部只保留模型切换、日志和 Git 菜单，不再放置五个大操作卡片。
2. 首页明确区分“操作记录”和“聊天消息”。
3. 单次网络调用直接平铺，不再套一层无意义的请求折叠框。
4. 来源只保留一层来源折叠；来源内的收藏、记忆记录和聊天消息均直接平铺，不再逐条嵌套点击。
5. 原始请求 JSON 放在最末，作为核对信息，不抢占主要阅读路径。
6. 写入结果优先显示自然语言实际内容，内部 ID 不在主界面展示。

## 数据保留边界

- 操作历史最多 20 条。
- 最近 8 条默认显示，可继续显示到 20 条。
- 最新记录优先保留完整请求和来源正文；旧记录在会话存储预算不足时会压缩，并在界面明确提示正文未保留。
- 单条写入变化正文最多保存 4000 字符，超过部分明确标记截断。
- 普通模型请求不再按 16000 字符二次截断；超大单项仍有 24 万字符保护上限。
