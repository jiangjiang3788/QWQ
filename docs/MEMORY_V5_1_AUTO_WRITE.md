# 动态记忆 V5.1：完整轮次与短期自动写入

## 本版边界

V5.1 不改变 V5.0 已确定的九张表、六个公共字段和内部元数据结构，只接入聊天轮次、短期自动写入、旧行匹配及每轮结果反馈。

仍未启用：

- 事项总结与思想成长总结的短期压缩
- 已压缩短期记录的停止发送和批量清理
- 从中期总结生成长期草稿

以上属于 V5.2。

## 一轮的定义

一次正常 AI 回复对应一个 `memoryRoundId`：

```text
用户自上次 AI 回复后连续发送的全部消息
＋
AI 本次一次性生成的全部回复消息
＝
一个完整轮次
```

AI 开始回复前，程序已经把本轮所有用户消息标为同一轮，并使用整批用户消息：

- 匹配需要注入的相关记忆
- 搜索 Rows 表的旧记录候选
- 生成动态表写入协议

AI 回复结束后，本次生成的所有 AI 消息补入同一轮。

模型输出记忆操作时，被明确要求先决定完整可见回复，再结合本轮用户消息和它本轮形成的有效结论，统一判断要写入哪些表。

## 自动写入表

V5.1 自动检查五张表：

1. 当前状态
2. 近期事项
3. 想法与启示
4. 物品
5. 日常观察

每张表独立判断。当前状态更新不能代替其他表；同一条信息符合多张表时，可以在同一轮生成多条操作。

AI不能写入：

- 核心档案
- 事项总结
- 思想与成长总结
- 稳定长期记忆

AI也不能删除任何正式记录。

## 写入协议

AI可见回复末尾追加：

```text
<memory_ops>{"operations":[...]}</memory_ops>
```

无更新时仍输出：

```text
<memory_ops>{"operations":[]}</memory_ops>
```

操作示例：

```json
{
  "tableId": "v5_recent_events",
  "action": "upsert",
  "recordId": "memory_record_xxx",
  "source": "用户明确",
  "values": {
    "事项状态": "已完结",
    "结果": "报告已经提交"
  }
}
```

更新旧记录时只提交本轮变化字段，不复制整行旧值。

## 合理新增和更新

代码根据本轮全部用户消息，给每张 Rows 表筛选少量候选：

- 近期事项、想法、物品：最多 6 条，以相关记录优先，并补少量最近记录
- 日常观察：最多 3 条
- KV 当前状态：提供最近状态项，最多 20 条

候选包含 `recordId` 和表模板指定的身份/上下文字段。

AI判断是同一事项时使用候选 `recordId` 更新；属于独立新内容时新增。找不到候选不会阻止新增。

代码执行顺序：

```text
recordId
→ 显式 match
→ 身份字段完全匹配
→ 找不到则新增
```

## 无变化不更新

若提交值与旧值完全一致：

- 不修改 `updatedAt`
- 不修改可见“时间”
- 不改变 `roundId`
- 不显示绿点
- 返回 `checked`

因此当前状态不会为了表示“本轮检查过”而伪造更新。

## 分类、标签和来源

分类、标签仍由用户在表模板中提供提示。AI按表设置可以补充新分类或新标签，它们不作为写入门槛。

来源只有：

- `用户明确`：用户直接说出的事实、决定、需求或观点
- `AI判断`：AI归纳出的理解、判断或未来指导

来源与本地时间由写入器统一落表，时间精确到秒。

## 日常观察的当前策略

日常观察仍是一条观察一行。本版不发送几十条健康历史：

- 写入候选最多 3 条
- 上下文相关引用最多 3 条
- 当前轮没有相关内容时，不引用日常观察
- 没有明确数字时不补数字

趋势压缩等复杂健康设计留待真实数据量增加后再做。

## 每轮提示和绿点

全局设置中可开关“每轮显示记忆处理结果”。默认开启。

结果包括：

- 本轮已更新
- 本轮没有需要更新的内容
- 指令被拒绝及首个原因
- memory_ops 解析失败

表名绿点表示该表本轮有正式变化；Rows 的绿点显示在具体变化内容单元格；KV 显示在本轮变化记录旁。下一轮无更新时，上一轮绿点不会继续显示。

## 上下文匹配

相关记忆使用当前用户批次进行轻量文字匹配；没有新用户消息的后台场景才回退到最近完整轮次。

匹配参考：

- 分类
- 标签
- 标题
- 表模板指定的上下文字段
- “始终注入”标签
- “禁止注入”标签
- 表的有效天数

没有恢复向量数据库或额外 AI 检索调用。
