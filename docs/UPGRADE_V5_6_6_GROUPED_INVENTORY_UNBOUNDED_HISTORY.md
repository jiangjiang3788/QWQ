# QWQ V5.6.6：同类盘点、历史无上限与长内容滚动修复

## 本次重新核查得到的根因

### 收藏数量为什么会出现“用户 16、角色 192，但只有 120 条明细”

不是收藏数据库只读取了 120 条，也不是标题随便估算。根因在 `js/modules/operation_runtime.js`：旧版 `safeClone()` 对所有数组统一执行 `slice(0, 120)`。最终请求的 `contextManifest.sources[].items` 在进入操作记录时被截断，因此标题仍来自请求中的真实计数 208，而悬浮球只能拿到前 120 条明细。

V5.6.6 将克隆策略拆成两类：

- 最新网络请求、请求消息数组、`contextManifest`、`promptTrace` 使用完整数组克隆；
- 较旧操作记录仍可按存储预算压缩，但会明确显示保留数量，不再把截断后的数量冒充完整数量。

专项回归使用“用户 16 条 + 角色 192 条 = 208 条”验证，操作运行时和最终来源清单均保留 208 条。

## 1. 收藏和记忆按同类二级分组

### 收藏

一级标题仍为“收藏盘点”，一级默认收起。展开后只有两个二级折叠组：

- 用户收藏；
- 角色收藏。

每个二级组内部直接平铺实际收藏正文，不再为每一条收藏生成一个折叠框。一级摘要显示用户数、角色数和总数；二级摘要显示该类实际总数。

### 结构化记忆

一级标题仍为“结构化记忆”。展开后按记忆表名称生成二级折叠组，例如“关系状态”“近期事项”。同一表内的记录直接平铺为“第 1 条、第 2 条”，不再一条记录一个折叠框。

世界书等确实需要逐条选择查看的来源仍保留条目级折叠，不与收藏、记忆混用同一规则。

## 2. PROMENT 私聊历史取消 200 条上限

旧路径存在三层限制：

1. PROMENT 输入框 `max="200"`；
2. 上下文编译器把历史条数硬限制在 500；
3. 私聊请求组装前又先执行 `chat.history.slice(-chat.maxMemory)`，导致 PROMENT 即使设得更大，也可能先被角色的 `maxMemory` 截断。

V5.6.6 已同时处理三层：

- PROMENT 输入框不再设置最大值；
- 编译器不再设置 500 条硬上限；
- 私聊文本请求的预切片改由 PROMENT 统一控制，不再受角色 `maxMemory` 二次限制。

现在的规则：

- `0`：发送当前节点或当前聊天中全部可用历史消息；
- 正整数：按最终消息条目保留最近 N 条；
- 关闭“聊天历史”：仅由最终编译器保留本轮用户输入。

这是消息条数，不是对话轮次。实际可发送长度仍会受到所选模型上下文窗口、接口网关限制和请求体大小的客观约束；程序本身不再人为限制为 200 或 500。

## 3. 长内容展开后的滚动覆盖修复

旧版全屏面板本身滚动，同时顶部标题和操作区使用 `position: sticky`，来源正文又有自己的 `max-height + overflow:auto`。三个滚动层叠加后，长条目下滑时会出现正文穿过或被标题覆盖的视觉问题。

V5.6.6 改为单一滚动模型：

- 全屏面板为纵向 Flex 容器并禁止自身滚动；
- 标题区和操作区不再 sticky 叠层；
- 只有 `.quick-dock-panel-content` 负责页面滚动；
- 来源正文取消内部最大高度和嵌套滚动。

因此长收藏、长记忆、长系统规则均随页面自然向下延伸，不会覆盖后面的来源标题。

## 4. 收藏计数口径

计数顺序现在固定为：

1. 从最终 system prompt 的 `<user_favorites count>` 和 `<character_favorites count>` 读取本次真实发送数量；
2. 同时把对应实际条目写入来源清单；
3. 来源注册表保留 `count`、`favoriteCounts` 和完整 `items`；
4. 悬浮球一级和二级摘要都使用同一组计数元数据。

收藏读取还会按收藏记录 ID 去重，避免同一数据库记录被重复盘点。当前角色收藏只读取当前角色自己的记录；用户收藏继续服从角色的“当前会话/全部会话”可见范围设置。

## 兼容说明

V5.6.5 期间已经保存到 `sessionStorage`、且当时被截成 120 条的旧操作记录无法从截断数据中恢复缺失正文。V5.6.6 会在旧记录的分类计数大于当前保留明细时显示“当前记录保留 X/Y 条”。安装 V5.6.6 后产生的新请求会完整记录。

数据结构版本仍为 `STORE_VERSION=3`，覆盖程序文件不会主动清空收藏、聊天或结构化记忆。
